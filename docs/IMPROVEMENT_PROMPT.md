# Профессиональный промт по улучшению сайта WebMu и пользовательской панели

> **Назначение документа.** Этот файл — готовый, структурированный промт (Technical Brief / Specification),
> который можно передать ИИ-агенту, разработчику или подрядной команде для пошагового улучшения
> веб-фронтенда WebMu (PHP, MS SQL Server через ODBC, MuOnline Season 3 Ep.1).
>
> **Базовый контекст проекта.** WebMu — единый front-controller (`index.php`), маршрутизация
> через `?m=...`, модули в `modules/`, виджеты главной в `modules/widgets/`,
> шаблоны в `themes/ex/pages/`, общий CSS — `assets/css/site.css`,
> доступ к БД — только через `db_query() / db_one() / db_all() / db_exec()`
> (параметризованный ODBC), конфигурация — `opt.php` (git-ignored, шаблон — `opt.example.php`).
>
> **Целевая среда.** PHP 7.4+/8.x с расширением `odbc`, ODBC-драйвер `Driver={SQL Server}`,
> MuOnline Season 3 Ep.1 (стоковая схема `MuOnline` + опциональные WebMu-таблицы).
>
> **Принцип приоритизации.** Пункты упорядочены **от наиболее важных к наименее важным**.
> Внутри каждого раздела подпункты также отсортированы по убыванию критичности.
> Сначала — безопасность и корректность данных, затем — стабильность ключевых модулей
> (рейтинг, аккаунт, донат, голосование, маркет), затем — UX/визуал, затем — расширения.

## 1. Безопасность и целостность данных (критично, P0)

Без выполнения этого блока запрещено выкладывать сайт в публичный доступ.

1.1. **SQL-инъекции — нулевая толерантность.**
  - 1.1.1. Проверить, что **все** запросы идут через `db_query() / db_one() / db_all() / db_exec()` из `core/db.php` (параметризация через `odbc_prepare + odbc_execute`).
  - 1.1.2. Запретить любую конкатенацию пользовательского ввода в SQL — code review + grep по `"SELECT ' . $"` и аналогам.
  - 1.1.3. Для динамических идентификаторов (имя таблицы/колонки из конфига) использовать только `db_ident()` с белым списком из `opt.php`.

1.2. **CSRF и honeypot.**
  - 1.2.1. Каждый POST-маршрут должен присутствовать в `$state_changing` в `index.php` и валидироваться `csrf_field()` / соответствующей проверкой токена.
  - 1.2.2. Honeypot-поле должно быть скрыто CSS, не `display:none` через JS, и обязательно проверяться на сервере.
  - 1.2.3. После неуспешной проверки — редирект на видимую форму (через `$back`-карту), а не белый экран.

1.3. **Аутентификация и сессии.**
  - 1.3.1. Cookies сессии: `HttpOnly`, `Secure` (если HTTPS), `SameSite=Lax` (или `Strict` для админки).
  - 1.3.2. Регенерация `session_id()` после успешного логина и смены пароля.
  - 1.3.3. Хеш-проверка пароля строго через серверную логику MuOnline (если стоковая — учитывать кодировку и обрезку до 10 символов в `memb__pwd`).
  - 1.3.4. Rate limit на `login` и `register` (уже частично реализован в `core/auth.php`) — расширить на `vote`, `donate`, `change_password`, `buy`.

1.4. **Валидация и санитизация ввода.**
  - 1.4.1. На входе — белые списки (логин: `[A-Za-z0-9]{4,10}`, имя персонажа — по правилам сервера).
  - 1.4.2. На выходе — `htmlspecialchars($v, ENT_QUOTES, 'UTF-8')` для всего, что попадает в HTML; отдельный экран для атрибутов и URL.
  - 1.4.3. Запретить отображение «сырых» имён гильдий/персонажей с произвольным Unicode без нормализации.

1.5. **Секреты и конфигурация.**
  - 1.5.1. `opt.php` остаётся в `.gitignore`; добавить CI-проверку, что файл не попал в индекс.
  - 1.5.2. Убедиться, что SQL-логин WebMu имеет права **только** `SELECT/INSERT/UPDATE` на нужные таблицы — никогда `sa`/`db_owner`.
  - 1.5.3. Логи (`logs/db.log`) не должны содержать пароли и полные строки подключения.

1.6. **Защита от повторных списаний и race conditions.**
  - 1.6.1. Все операции списания валюты (`buy`, `donate`, `vote_callback`) — в транзакции с `BEGIN TRAN ... COMMIT/ROLLBACK` и проверкой остатка **внутри** транзакции (`UPDATE ... WHERE balance >= ?`).
  - 1.6.2. Идемпотентные ключи для callback'ов платёжек и голосовалок (уникальный индекс по `tx_id` / `vote_token`).

## 2. Корректность ключевых модулей — без ошибок и багов (P0)

Цель: ни один модуль не должен падать с SQL Server warning, не должен показывать «битые» данные и не должен зависеть от того, какие именно дополнительные таблицы есть в БД.

### 2.1. Модуль «Рейтинг» (`modules/ranking.php`) — приоритет 1

  - 2.1.1. **Фильтры обязательны на всех вкладках:**
    - Исключать `CtlCode IN (1, 17)` (бан и скрытый GM).
    - Исключать персонажей с пустым/служебным именем.
    - Учитывать настраиваемое имя колонки grand-reset (`gr_res` на кастомных схемах S3 vs `GReset` стоковой) — брать из `$config['char_greset_col']`.
  - 2.1.2. **Корректные JOIN.**
    - Все varchar-JOIN между `Character.Name` и `GuildMember.Name` (и аналогичные) — с `COLLATE DATABASE_DEFAULT` на **обеих** сторонах, иначе падение `SQL_Latin1_General_CP1_CI_AS vs Latin1_General_CI_AS`.
    - Не алиасить `c.Name AS Name` — использовать уникальный алиас (`[CharName]`) и ремапить в PHP, чтобы избежать «Ambiguous column name 'Name'» под `SQL_CUR_USE_ODBC`.
  - 2.1.3. **Вкладка «Online».**
    - Определять онлайн-персонажа через `AccountCharacter.GameIDC` ↔ `MEMB_STAT.memb___id`, а не через `Character.AccountID = MEMB_STAT.memb___id` (последнее даёт всех персонажей аккаунта, а не текущего).
    - Если `AccountCharacter` отсутствует — корректный fallback с предупреждением, без 500.
  - 2.1.4. **Вкладка «Гильдии».**
    - `Guild.G_Mark` (`image`) и `G_Notice` (`text/ntext/varbinary`) **нельзя** использовать в `GROUP BY` — считать `members_count` через подзапрос по `GuildMember`, а уже потом джойнить к `Guild`.
    - Эмблему гильдии отдавать как PNG через отдельный route (`?m=guild_mark&id=...`) с корректным `Content-Type: image/bmp` → конвертация в PNG (или хотя бы `image/x-ms-bmp`).
  - 2.1.5. **Сортировки и пагинация.**
    - Стабильная сортировка с тай-брейкером по `Name` (иначе на равных значениях SQL Server возвращает разный порядок между страницами).
    - `OFFSET ... FETCH NEXT` или `ROW_NUMBER()` — выбрать одно и применять единообразно; ограничить `perPage` (например 10/25/50/100) на сервере.
    - Запрет `ORDER BY <ordinal>` — только по именам колонок.
  - 2.1.6. **Курсоры ODBC.**
    - Использовать `SQL_CUR_USE_DRIVER` (cursor type 2); `SQL_CUR_USE_ODBC` ломает `SQLGetData` на алиасах вроде `total_resets`.
  - 2.1.7. **Кэширование.**
    - Кэш в `cache/` на 30–120 секунд для тяжёлых вкладок (Top по resets, Top guilds), с инвалидацией по таймеру и кнопкой «обновить» для админа.
  - 2.1.8. **Тесты-смоки.** Скрипт, который для каждой вкладки рейтинга делает один запрос и проверяет: 200 OK, нет PHP warning, не пустой набор колонок, нет коллизий collation.

### 2.2. Модуль «Аккаунт / Личный кабинет» (`modules/account.php`, `modules/character.php`)

  - 2.2.1. Балансы (zen, credits, wcoin, goblin points, gp, ruud) брать **только** через ключи `$config['cr_*'] / ['usd_*'] / ['wcoin_*'] / ['gr_*']`, а не из жёстко зашитых имён.
  - 2.2.2. Гейтить любые «новые» поля (`IsVaultPin`, `AccountLevel`, `MasterLevel`, `cash`, `usd`, `QuestNumber`) через `db_column_exists()` / `db_table_exists()` — стоковая `MuOnline_Bak` Season 3 их не содержит.
  - 2.2.3. **Инвентарь.** Декодирование 12 экипированных слотов × 12 байт по правилам S3 Ep.1 (см. `mu_decode_item_identity` / `mu_parse_equipped_inventory`):
    - `group = (b0>>5) + (b9 & 0x80 ? 8 : 0)`,
    - `code  = (b0 & 0x1F) + (b9 & 0x40 ? 32 : 0)`,
    - `b1`: skill(7) | level(6-3) | luck(2) | opt(1-0),
    - `b7` exc-mask = биты 0–5.
  - 2.2.4. Смена пароля — двойной ввод нового, подтверждение текущего, сравнение через `hash_equals`, обнуление сессий других устройств (если используются).
  - 2.2.5. Привязка к персонажу — проверять, что выбранный char действительно принадлежит залогиненному `memb___id`.
  - 2.2.6. История операций (последние 50): покупки, голоса, донаты, смены пароля — отдельная таблица `webmu_log` (см. `docs/schema_addons.sql`).

### 2.3. Модуль «Регистрация» (`modules/register.php`, `modules/registration.php`)

  - 2.3.1. Уникальность `memb___id` на уровне БД (UNIQUE-индекс), а не только PHP-проверкой.
  - 2.3.2. Пароль — только ASCII-печатаемые, длина по правилам сервера (часто 4–10 для стока).
  - 2.3.3. Проверка email-формата, опционально подтверждение по почте (через токен в `webmu_email_confirm`).
  - 2.3.4. Стартовые награды (zen/credits) — выдавать в той же транзакции, где создаётся `MEMB_INFO`, чтобы не было «полусоздания».

### 2.4. Модуль «Голосование» (`modules/vote.php`, `modules/vote_callback.php`)

  - 2.4.1. Список сайтов и награды — из `opt.php`, без хардкода.
  - 2.4.2. Колбек — проверка подписи/IP сайта-голосовалки, идемпотентность по `vote_id`.
  - 2.4.3. Антифрод: не более N голосов в сутки на один аккаунт, на один IP, на одну пару (account+site).
  - 2.4.4. Прозрачное логирование причины отказа (для пользователя — общая, для админа — детальная в `logs/`).

### 2.5. Модуль «Донат» (`modules/donate.php`, `modules/buy.php`)

  - 2.5.1. Цены, пакеты, валюты — целиком из конфига; никаких чисел в шаблоне.
  - 2.5.2. Покупки атомарны (см. 1.6.1), проверка достатка валюты — внутри `UPDATE`.
  - 2.5.3. Выдача предметов в `Warehouse` (vault) — корректное байтовое выравнивание под S3 Ep.1, проверка свободного слота.
  - 2.5.4. История транзакций видна пользователю; админу — отдельный отчёт.

### 2.6. Модуль «Маркет» (`modules/market.php`)

  - 2.6.1. Фильтры по типу/уровню/опциям — через параметризованные запросы.
  - 2.6.2. Проверка владения предметом перед выставлением, блокировка слота (флаг `is_listed`), снятие — корректный возврат.
  - 2.6.3. Покупка — атомарная: списание валюты у покупателя, начисление продавцу, перенос предмета — в одной транзакции.
  - 2.6.4. Защита от двойной покупки одного лота (UNIQUE по `lot_id` в `webmu_market_tx`).

### 2.7. Виджеты главной (`modules/widgets/*`)

  - 2.7.1. `server_status.php` — таймаут на TCP-проверку 1–2 сек., кэш 30 сек., не блокировать рендер.
  - 2.7.2. `top5guild.php`, `top5items.php`, `strongest.php`, `questtop.php`, `lastinf.php` — те же правила COLLATE и фильтра CtlCode, что и в рейтинге.
  - 2.7.3. Если виджет упал — показывать аккуратный плейсхолдер «временно недоступно», а не PHP warning.

## 3. Стабильность, наблюдаемость, эксплуатация (P1)

3.1. **Единая обработка ошибок.**
  - 3.1.1. `set_error_handler` + `set_exception_handler` → лог в `logs/php.log`, пользователю — нейтральная страница.
  - 3.1.2. Включить `display_errors=Off` на проде, `log_errors=On`.
  - 3.1.3. ODBC-ошибки логируются в `logs/db.log` с SQLSTATE и (для админа) текстом запроса без значений параметров.

3.2. **Логирование действий.**
  - 3.2.1. Таблица `webmu_log(id, ts, ip, account, action, details JSON)`.
  - 3.2.2. Логировать: login (успех/неуспех), register, change_password, vote, donate, buy, market_list/sell/buy.

3.3. **Метрики и мониторинг.**
  - 3.3.1. Endpoint `?m=health` (без `insite`-гейта на чтение) — отвечает 200, проверяет коннект к БД и доступность критичных таблиц.
  - 3.3.2. Счётчики: онлайн, регистрации/час, голоса/час, ошибки/час.

3.4. **Производительность.**
  - 3.4.1. Индексы под топовые запросы (resets DESC, level DESC, MasterLevel DESC, Money DESC).
  - 3.4.2. Кэш виджетов главной 30–60 сек.
  - 3.4.3. HTTP-кэш для статики (`assets/`) — 7+ дней, с версионированием по mtime/?v=hash.
  - 3.4.4. Сжатие (gzip/br) на уровне веб-сервера.

3.5. **CI/проверки.**
  - 3.5.1. `find . -name '*.php' -print0 | xargs -0 -n1 php -l` — обязательный шаг в CI.
  - 3.5.2. Линтер шаблонов на наличие сырого `echo $var` без экранирования.
  - 3.5.3. Smoke-тесты основных страниц (см. 2.1.8).

3.6. **Резервные копии и миграции.**
  - 3.6.1. `docs/schema_addons.sql` поддерживать в актуальном состоянии и применять идемпотентно (`IF NOT EXISTS`).
  - 3.6.2. Регулярные бэкапы и инструкция восстановления в `docs/setup.html`.

## 4. Пользовательская панель (Личный кабинет) — расширение функционала (P1–P2)

Все пункты ниже — поверх базового аккаунта; реализовывать после 1–3.

4.1. **Главная панели.**
  - 4.1.1. Карточка аккаунта: логин, дата регистрации, последний вход (IP/время), статус (active/blocked/vip).
  - 4.1.2. Виджет балансов (zen, credits, wcoin, ruud, gp) — иконка + значение + кнопка «пополнить».
  - 4.1.3. Виджет «мои персонажи» с миниатюрой класса, lvl/reset/master, гильдией, статусом онлайн.

4.2. **Безопасность аккаунта.**
  - 4.2.1. Смена пароля.
  - 4.2.2. Смена email с подтверждением по старому и новому.
  - 4.2.3. Привязка PIN-кода для склада/доната (если `IsVaultPin` существует) и сброс PIN с верификацией.
  - 4.2.4. История входов: дата, IP, User-Agent, гео-страна.
  - 4.2.5. Кнопка «выйти на всех устройствах» (инвалидирует все сессии аккаунта).
  - 4.2.6. Опционально 2FA по TOTP (Google Authenticator) — отдельная таблица `webmu_2fa`.

4.3. **Управление персонажами.**
  - 4.3.1. Просмотр статов и экипировки (декод инвентаря из 2.2.3).
  - 4.3.2. Разблокировка персонажа (`Connected` застрял), с rate limit (раз в N минут).
  - 4.3.3. Сброс позиции (warp в Lorencia/Noria) при наличии прав.
  - 4.3.4. Переименование персонажа за валюту (если разрешено сервером) — атомарно, с проверкой коллизий имени.
  - 4.3.5. Смена внешности/класса — только если поддержано серверной логикой.

4.4. **Финансы и магазин.**
  - 4.4.1. Кошелёк: история начислений и списаний с фильтром по типу валюты и периоду.
  - 4.4.2. Донат-пакеты с описанием бонусов и кнопкой «купить».
  - 4.4.3. Промокоды (таблица `webmu_promo` с лимитом активаций и сроком).
  - 4.4.4. Реферальная программа: уникальная ссылка, бонус приглашающему за регистрацию + достижение N резетов приглашённым.

4.5. **Голосование и награды.**
  - 4.5.1. Прогресс «голосов сегодня / в неделю», ближайшее окно следующего голоса.
  - 4.5.2. Ежедневный/недельный бонус за серию голосов.

4.6. **Маркет в панели.**
  - 4.6.1. «Мои лоты» с фильтрами active/sold/expired и кнопкой снятия.
  - 4.6.2. «Мои покупки» с историей.
  - 4.6.3. Уведомления при продаже лота (внутри панели + опционально email).

4.7. **Поддержка.**
  - 4.7.1. Тикет-система: создание, переписка, статусы (open/answered/closed).
  - 4.7.2. FAQ с поиском.

4.8. **Уведомления.**
  - 4.8.1. Колокольчик в шапке панели; типы: security, finance, market, support, system.
  - 4.8.2. Настройка каналов: сайт / email.

## 6. UX, визуал, доступность (P2)

6.1. **Адаптивность.**
  - 6.1.1. Брейкпоинты 360 / 768 / 1024 / 1440.
  - 6.1.2. Мобильное меню-бургер, тач-таргеты ≥ 44×44 px.

6.2. **Темизация.**
  - 6.2.1. Light/Dark переключатель (CSS-переменные).
  - 6.2.2. Сохранение выбора в `localStorage` + `prefers-color-scheme`.

6.3. **Типографика и сетка.**
  - 6.3.1. Единый ритм отступов (4/8 px grid).
  - 6.3.2. Контраст не ниже WCAG AA (4.5:1 для текста).

6.4. **Z-index и события.**
  - 6.4.1. Декоративные `::before/::after` (`.panel-corner` и т.п.) — обязательно `pointer-events: none`, иначе блокируются клики (например, кнопка регистрации).
  - 6.4.2. Кнопки `.btn` — `z-index: 2; pointer-events: auto;`.

6.5. **Доступность.**
  - 6.5.1. `alt` у всех осмысленных изображений, пустой `alt=""` у декоративных.
  - 6.5.2. `<label for>` для всех инпутов, явные `aria-*` для виджетов.
  - 6.5.3. Навигация с клавиатуры по всем интерактивным элементам, видимый focus-ring.

6.6. **Микро-UX.**
  - 6.6.1. Тосты вместо `alert()`.
  - 6.6.2. Прогресс-индикаторы для долгих действий (покупка, голос).
  - 6.6.3. Подтверждение опасных действий (смена пароля, снятие лота).

## 10. Критерии приёмки (Definition of Done)

Любая фича считается завершённой, только если выполнены **все** условия:

- [ ] Нет PHP warning/notice на тестовых данных (`display_errors=On` в dev).
- [ ] Нет SQL-warning'ов SQL Server: collation, ambiguous column, GROUP BY на text/image, конверсия типов.
- [ ] Все формы защищены CSRF + honeypot, все запросы — параметризованы.
- [ ] `php -l` проходит на всех изменённых файлах.
- [ ] Smoke-тесты (см. 2.1.8) зелёные.
- [ ] Изменения отражены в `docs/` (setup/CHANGELOG/при необходимости README).
- [ ] Конфиг-ключи добавлены в `opt.example.php` с комментарием.
- [ ] Опциональные таблицы/колонки гейтятся через `db_table_exists()` / `db_column_exists()`.
- [ ] UI проверен на 360 / 768 / 1440 px и в Light/Dark теме.
- [ ] Логирование критичных действий присутствует в `webmu_log`.
